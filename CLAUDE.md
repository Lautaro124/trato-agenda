# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Trato (renamed from "Trato Agenda" — the domain is still `tratoagenda.com`): customer service over WhatsApp, delegated to an AI agent that should read like a person from the business (not a bot) while it does the management work — checking the agenda, quoting stock, sending payment links. Two modules, one per account: turnos and ventas. Monorepo: `api/` (NestJS 12 + Prisma 7 + Postgres 16) and `web/` (Next.js 16 onboarding frontend), wired together by `docker-compose.yml` (db :5432, api :4000, web :3000).

**Google login, WhatsApp-only signup, WhatsApp linking, Google Calendar, the local agenda, and the WhatsApp conversation itself are all real** — nothing is simulated anymore except the screen after linking. Google is optional: an account can be created just by scanning the WhatsApp QR, and then its agenda lives in Postgres (see "Two doors in" below). `/vincular` does a real Baileys QR pairing over SSE (`api/src/whatsapp/`), or, on a phone, pairing by code (see "`/vincular`: QR or code" below). `/contanos` (a wizard whose first step picks the assistant; for turnos it then asks nombre del titular, tipos de evento con duración, franja horaria, nombre del asistente) generates a real per-user agent via OpenRouter (`api/src/agents/`); that agent then answers incoming WhatsApp messages for real, checking availability and booking/cancelling/rescheduling on the owner's Google Calendar (`api/src/calendar/`, `api/src/conversation/`). There is no screen after linking — "Ir a mi agenda" restarts the demo.

A second kind of account exists: a **comercio** picks "Vender productos" in `/contanos` and gets a sales assistant instead (catalog with hybrid search, orders that reserve stock, optional client data for shipping, Mercado Pago links in the shop's own name, notifications, sales history). See "The commerce module" below.

UI copy is in Spanish (`<html lang="es">`, rioplatense voseo). Code comments are also in Spanish. Match that when editing.

## Commands

From the repo root — this is how you actually run the thing, since the login needs the API and the DB:

```bash
docker compose up --build
docker compose exec api npx prisma migrate dev --name init   # first time only
```

The API needs `api/.env` (never committed; the variable table is in the root `README.md`). Without real `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`, the API boots but Google rejects the consent screen.

Postgres credentials are not hardcoded in `docker-compose.yml` any more: `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` (and `NEXT_PUBLIC_API_URL`) come from an optional `.env` at the repo root — `.env.example` is the template, and every one of them has a default in the compose file, so `docker compose up` still works with no config. The same three build the `db` service's credentials **and** the `DATABASE_URL` handed to the API, so the two can't drift apart. None of that file matters in a deploy: there the platform provides `DATABASE_URL` and the API just reads it. The production image (`api/Dockerfile`, `prod` stage) runs `prisma migrate deploy` before `node dist/main`, which is why the Prisma CLI sits in `dependencies` — `npm prune --omit=dev` would strip it otherwise. `NEXT_PUBLIC_API_URL` is inlined at build time and only reaches a Dockerfile build through the `ARG` already declared in `web/Dockerfile`'s `build` stage.

Production lives on Railway (project `trato-agenda`): the Postgres plugin plus one service per folder, each with its `rootDirectory` and watch paths (`api/**`, `web/**`) so one side's push doesn't rebuild the other, both connected to `main` — a push is the deploy. The API service is pinned to a single replica with `sleepApplication: false`: `WhatsappService.onModuleInit` resumes every linked session at boot, so a second replica would fight over the same Baileys socket. The deploy variables and the manual steps (Google console, Mercado Pago webhook) are in the root `README.md`.

From `web/`:

```bash
npm run dev      # dev server on :3000
npm run build    # production build
npm run start    # serve the production build
npm run lint     # eslint (flat config, eslint-config-next core-web-vitals + typescript)
```

From `api/` (better via `docker compose exec api ...`): `npm run start:dev`, `npm run lint` (oxlint), `npm test` (vitest; the `*.db.spec.ts` files run real SQL and are skipped unless `TEST_DATABASE_URL` points to an already-migrated database with pgvector — CI's api job starts a `pgvector/pgvector:pg16` service for them; migrations are generated against that throwaway DB because `migrate dev` on the main one sees the LangGraph tables as drift), `npm run eval` (model evals against real OpenRouter — costs money, never part of `npm test`; see `api/evals/`).

GitHub Actions (`.github/workflows/`): `ci.yml` runs lint/types/tests/build for each package, builds both production images (and fails if one runs as root) and runs the Playwright E2E against the compose stack with a throwaway `api/.env`; `security.yml` runs `npm audit`, CodeQL, TruffleHog, Dependency Review, Grype on the images, an OWASP ZAP baseline (passive DAST) against the compose stack — same throwaway `api/.env` and e2e override as the E2E job; ignore rules go in `.zap/rules.tsv` — and actionlint. The dev-dependency `npm audit` step goes through `.github/scripts/npm-audit-con-excepciones.mjs`, which accepts the per-GHSA, per-folder (`en`) entries in `.github/npm-audit-excepciones.json` only while npm has no non-breaking fix and until each entry's `revisar` date — either one makes the job fail again; the production audit takes no exceptions. Third-party actions are pinned by commit SHA — keep it that way; Dependabot bumps them. `api/package.json` `overrides` pin patched transitive deps (`undici`, `mysql2`, `deepmerge-ts`, `tmp`); drop one only when its parent ships the fix. Findings and pending items: `docs/seguridad.md`.

Security validation before pushing: `.claude/settings.json` registers a `Stop` hook (`.claude/hooks/validar-seguridad.sh`) that, whenever a prompt leaves changes not yet on `origin/<branch>`, blocks the end of the turn and asks for the `revisor-seguridad` (vulnerabilities, what CodeQL `security-extended` would flag plus this repo's own controls) and `security-auditor` (secrets) subagents in `.claude/agents/` to run in parallel over those changes; fix every HIGH/MEDIUM finding before finishing. It fingerprints the diff (state in the gitignored `.claude/.validacion-seguridad`), so an already-reviewed diff passes and a fix gets reviewed again, capped at 3 rounds per prompt. Don't skip it. CodeQL `paths-ignore` (in `security.yml`) also leaves out `docs/agentes-whatsapp.html`, a generated archify diagram that is never deployed.

The web side has no unit test runner; it is covered end to end by `e2e/` (Playwright, its own `package.json` at the repo root, outside Railway's watch paths). From `e2e/`: `npm run e2e:stack` (compose with `docker-compose.e2e.yml`, project name `trato-e2e`, its own DB that migrates on boot), `npm run e2e` (desktop + mobile projects), `npm run e2e:real` (the single `@real` test, against real OpenRouter). The override adds `e2e/openrouter-stub/server.mjs`, a deterministic fake of the OpenAI-compatible endpoint. Agent generation (`/agents/generate`) never reaches it any more — it's a local template, not a model call. What the stub still fakes: conversation requests (they carry `tools`) follow a keyword script ("turno … soy X" → `crear_turno` next business day 10:00, "movelo" → `reprogramar_turno` 11:00, "cancel" → `cancelar_turno`, "dónde"/"dirección" → a text reply read from the `bloqueLugar` block), reading the titular and the first tipo de turno out of the `reglasDeAgenda` block the runtime always adds in code (not out of the generated prompt, so it doesn't care whether the `Agent` came from the template or the old meta-agent); and client-summary requests (no `tools`) get fixed text. The sales assistant is recognized by the `Reglas de venta de …` block and has its own script ("quiero N … soy X" → `crear_pedido` with the variant of the last search, plus `entrega` from "con envío"/"retiro" when the rules say the shop ships and `datosCliente` from `Etiqueta: valor;` pairs in the message (`datosDelPedido`, also sent with `pedir_variante` and `aceptar_presupuesto`) — or, when the rules carry `MARCA_A_MEDIDA` and the first product of the last search is a medida (`ultimaBusquedaAMedida`: its block says `a medida: se cotiza`), `registrar_solicitud` with the `[producto <id>]` of the last search and the `Pregunta: respuesta;` pairs as answers instead — unless the message names a fixed version of the last search (`versionesDeLaUltimaBusqueda`): then `pedir_variante` with it, or with "pero …" `registrar_solicitud` with that `varianteBaseId` and what follows "pero" as `cambios` —; with `MARCA_A_MEDIDA`, a search result whose made-to-order product "tiene foto" first calls `enviar_imagen_producto` for it and answers with the search after the photo, and fixed versions are answered as "De X tenemos <versión> a $ …", "cancel" → `cancelar_pedido`, "mi pedido"/"pagué" → `consultar_pedido`, "envío" outside a purchase → `derivar_consulta`, "foto" → `enviar_imagen_producto` with the `[producto <id>]` of the last search, "dónde queda"/"dirección"/"retir…"/"el local" → a text reply read from the `bloqueLocal` block (address and pickup, "no tenemos local", or `derivar_consulta` when the local was never filled in), with `MARCA_A_MEDIDA` "una persona"/"hablar con alguien" → `derivar_a_persona` and "dale"/"acepto"/"avancemos" → `aceptar_presupuesto` with the order the rules list as `cotizado`, owner-only "cuánto vendí"/"ventas de hoy" → `resumen_ventas`/`listar_ventas`, anything else → `buscar_productos`), and `/api/v1/embeddings` returns deterministic bag-of-words vectors. "qué tenés"/"qué productos" → `ver_catalogo` (its reply leaves out the lines marked "(ya le llegó en foto)"), "mostrame <categoría>" → `ver_catalogo { categoria }`, "descuento"/"promo"/"oferta" → `ver_descuentos`, a `registrar_solicitud`/`aceptar_presupuesto` result that asks to send a message verbatim is answered with exactly that message, a made-to-order search result with "Hacemos X a medida", and a tool result carrying the discount offer (`OFERTA_DE_DESCUENTOS`) makes the reply end with "Además tenemos algunos descuentos, si querés te los paso.". `/api/alpha/decisions` (Jev) scores each option by the words it shares with the client's messages, ties broken by the order given. `GET /__llamadas?titular=` lets a spec assert what the API sent. The override also adds `e2e/mercadopago-stub/server.mjs` (:4020): OAuth with PKCE (the authorization page redirects straight back with a code), `/checkout/preferences` (plus `PUT /checkout/preferences/:id` to expire one; an expired link can't be paid), a `/checkout/:id` page whose "Pagar" button approves the payment and sends the signed webhook (secret `e2e-webhook-secret`; `API_INTERNA` rewrites the `notification_url` origin to `http://api:4000` inside compose), and `/v1/payments/:id` + `/search`. The browser reaches it at `localhost:4020` (`MERCADOPAGO_AUTH_URL`), the API at `mercadopago-stub:4020` (`MERCADOPAGO_BASE_URL`). Sales helpers for specs live in `e2e/tests/ventas.ts`. Specs select by role/label (`aria-label`s were added for that), never `data-testid`, and each test gets its own dev user (`usuarioDev` fixture in `e2e/tests/fixtures.ts`), so nothing needs a DB reset.

## Stack

`web/`: Next.js 16 App Router (Turbopack), React 19, TypeScript strict, Tailwind CSS v4 (PostCSS plugin only — no `tailwind.config`), `qrcode` for QR generation. Path alias `@/*` → `web/src/*`. Its runtime env vars are `NEXT_PUBLIC_API_URL` and the optional `NEXT_PUBLIC_SENTRY_DSN`, both inlined at build time (the Dockerfile takes them as build args, plus `SENTRY_AUTH_TOKEN`/`SENTRY_PROJECT` for the source-map upload).

`api/`: NestJS 12 on ESM, Passport (`passport-google-oauth20` + `passport-jwt` reading the cookie), Prisma 7 with the `@prisma/adapter-pg` driver (connection URL in `prisma.config.ts`, generated client in `src/generated/prisma`), oxlint, vitest. The Google refresh token is stored AES-256-GCM-encrypted (`src/auth/token-crypto.ts`) and never leaves the API — `UsuarioPublico` (`src/auth/auth.types.ts`) is the only user shape the frontend sees. `googleapis` uses that same refresh token for real Google Calendar access (`src/calendar/`). `src/agents/` builds a new user's agent config (system prompt + allowed actions) with a deterministic template (`src/agents/agent-template.ts`, pure function `construirConfiguracion`) — no LLM call, no network, no timeout on the `/agents/generate` path. `AgentsService` just interpolates the wizard's five fields into a fixed prompt shape and always enables the full action catalog (there's no product rule that varies it by `tipoUso`/`tipoTitular`). Free-text fields from the user (titular, bot name, tipo de turno names) go through `JSON.stringify` before being interpolated, which delimits and escapes them so the model reads them as data rather than instructions — that reduces prompt-injection ambiguity, it doesn't eliminate the risk. On boot, `ActualizacionAgentesService` (`src/agents/actualizacion-agentes.service.ts`, pure rules in `actualizacion-agentes.ts`) rewrites every `Agent` that isn't on its type's current template (`PLANTILLA_VERSION` / `PLANTILLA_VENTAS_VERSION`, old meta-agent rows included) from the row's own fields — system prompt, `allowedActions`, `descripcion`, `templateVersion` — guarded by `updatedAt` so an owner's concurrent edit wins, skips rows whose `tiposEvento` can't feed the template, and logs one numbers-only line with the user count. So bumping a template version regenerates every agent on the next deploy, production included. `Agent.model` is nullable now: `null` means the config came from the template (`Agent.templateVersion` says which one); a non-null value is left over from an agent generated by the old meta-agent, before this change. `src/agents/openrouter.client.ts` (a small `fetch` wrapper, no SDK) still exists and is still exported by `AgentsModule` — the conversation runtime and its client-summary step are the ones that use it now. `src/conversation/` itself runs on LangGraph (`@langchain/langgraph` + `@langchain/openai`): its single LLM node talks to the OpenRouter endpoint through `ChatOpenAI` pointed at `https://openrouter.ai/api/v1` (`src/conversation/llm.provider.ts`), configured with `OPENROUTER_API_KEY`/`OPENROUTER_MODEL` (and `OPENROUTER_BASE_URL`, which only the E2E stack changes), deliberately untied to one AI provider. The default model is `google/gemma-4-31b-it`, and the conversation runtime calls it with OpenRouter's unified `reasoning` parameter (`{ effort: 'low', exclude: true }` in `llm.provider.ts`) so it reads how people actually write on WhatsApp; the client-summary call is mechanical and passes `reasoning: { enabled: false }` instead. Any replacement model has to support both `tools` and `reasoning`. Every call carries `provider: { data_collection: 'deny', zdr: true }` — `POLITICA_DE_PROVEEDOR`, exported from `openrouter.client.ts` and imported by `llm.provider.ts` so the two cannot drift. That is Google's Limited Use requirement in code and not only in `/privacidad`: it restricts routing to providers that neither retain prompts nor train on them. It also shrinks the eligible provider set, so a model with no ZDR endpoint stops being available — run `npm run eval` before changing `OPENROUTER_MODEL`. `resumenDeError` (same file) is why LLM failures are logged as a capped `name: message` string instead of the error object: a provider's error body can echo the prompt, and the prompt carries the client's conversation. `llm.provider.ts` also mounts `fetchQueRechazaRespuestasVacias` (`src/conversation/respuesta-sin-choices.ts`): OpenRouter sometimes answers HTTP 200 with no `choices` when the provider blocks or fails, which LangChain turns into `TypeError … reading 'message'` (Sentry TRATO-API-2); the wrapper turns it into an HTTP error with the body's code, and `ConversacionNode` classifies it (`clasificarFalloDelModelo`) as `rechazo_contenido` / `sin_respuesta`, logged as a Sentry **warning** through `avisarASentry` (`src/observabilidad/aviso-a-sentry.ts`, fingerprint `modelo-sin-respuesta`, codes only, never the client's text) and answered with `MENSAJE_FUERA_DE_ALCANCE` or the generic apology. See `docs/seguridad.md`.

**Sentry** (errors + 10% traces in production, no Session Replay) is optional everywhere: without `SENTRY_DSN` (API) / `NEXT_PUBLIC_SENTRY_DSN` (web, inlined at build) nothing initializes. The API loads `src/instrument.ts` with `node --import ./dist/instrument.js` (Dockerfile `CMD`, `start:prod`, `start:dev` via `--exec`) because in ESM that is the only way to hook express/http/pg before they're imported; that's also why it reads `process.env` directly instead of going through `validateEnv`. `SentryModule.forRoot()` + `SentryGlobalFilter` (`APP_FILTER`) report non-`HttpException` errors, and `LoggerConSentry` (`src/observabilidad/logger-con-sentry.ts`, installed with `app.useLogger`) turns every `logger.error` into a Sentry event — that's how the errors caught and logged in Baileys, the graph, the sweeps and the webhooks reach Sentry without touching each `catch` (it skips `ExceptionsHandler` to avoid duplicates with the filter, and fingerprints text-only messages without their ids). Privacy is enforced in code because `/privacidad` and `docs/verificacion-google.md` promise it: SDK v11 collects everything by default, so `dataCollection` turns it all off, `INTEGRACIONES_DE_IA` removes every AI integration (prompts carry client conversations and Calendar data), and `limpiarEvento` / `limpiarSpan` / `limpiarBreadcrumb` (`src/observabilidad/scrubbing.ts`, tested; hand-copied in `web/src/lib/sentry.ts`) replace phones/emails, strip URL queries and keep only `user.id`. Spans are scrubbed in `beforeSendSpan`: with v11's default `traceLifecycle: 'stream'`, `beforeSendTransaction` never runs. Never re-enable an AI integration, Replay or a `dataCollection` category without updating both documents. The web side is `src/instrumentation-client.ts`, `src/instrumentation.ts` (`onRequestError`), `src/app/global-error.tsx` and `withSentryConfig` (from `@sentry/nextjs/config`) in `next.config.ts`, which uploads and deletes source maps only when the build has `SENTRY_AUTH_TOKEN`.

`web/AGENTS.md` (imported by `web/CLAUDE.md`) is auto-generated and rewritten by `next dev`. It warns that this Next.js version differs from training data — consult `web/node_modules/next/dist/docs/` before writing Next-specific code, and commit AGENTS.md changes along with your work rather than reverting them.

## Architecture

**Three-step onboarding flow.** `/` redirects to `/entrar`; `/entrar` offers two doors: "Continuar con WhatsApp" (`/entrar/whatsapp`, see below) or the API's `GET /auth/google`, whose OAuth callback redirects back to `/contanos` (the "Tu asistente" stage of the header's "Cuenta · Tu asistente · WhatsApp"). That screen is one wizard for both assistants. Step 1 is the choice itself (`ElegirAsistente.tsx`: "Agendar turnos" / "Vender productos", with the warning that the type can't change later), and it decides the rest: `pasosDe(tipo, atencion)` in `useOnboarding.ts` builds the steps: turnos asks "¿Cómo atendés?" right after "Tu negocio" (`ElegirAtencion.tsx`, same card format as step 1: Uno a uno · En grupo · Las dos cosas, `Atencion` = `individual | grupal | ambas`, preselected Uno a uno), then "¿Dónde atendés?" (`ControlesLugar.tsx`, see "Lugar de atención" below), and then shows "Qué turnos das" + "Horarios" for individual, "Tus clases" for grupal, or all three for ambas — so turnos has seven steps uno a uno, six en grupo, eight con las dos; ventas has five (qué va a hacer, tu negocio, tu local, datos del cliente — optional —, tu asistente): whether it sells stock or made-to-order is decided by each product, not the account (see "Stock y a medida en la misma cuenta" below). Switching type in step 1 keeps the titular and bot names. "Tu negocio" is the titular (persona o negocio; ventas is always negocio). "Qué turnos das" holds the tipo de uso as an inline "Empezar con: Ideas para consultorio | Mi propia lista" radio (`EmpezarCon`, `TIPOS_USO`) — no longer a step of its own; changing it resets the chosen tipos. Only consultorio/otro are offered — `comercio`, `reuniones`, `visitas` y `personal` ya no se ofrecen pero `agent-catalog.ts` los sigue aceptando en `TIPOS_USO_RETIRADOS`, por los `Agent` ya guardados; `/reuniones` los trata como `otro`. Each tipo de evento has its duración and an optional precio en pesos (`TipoEvento.precio`, dentro de la columna Json `Agent.tiposEvento`, sin migración; cada fila tiene un botón "Sin precio" que lo borra y traba el campo — `DatosEvento.sinPrecio`, sólo de pantalla, nunca viaja —, y el bloque "Mismo precio para todos" también lo aplica a todas; el runtime lo pone en `reglasDeAgenda` y `reglasDeAlcance` deja que el bot lo informe, y lo que no tiene precio sigue derivándose al titular). En el wizard las clases grupales (LAU-13) tienen su propio paso, "¿Qué clases das?" (`ListaClases.tsx` + `useClases.ts`): arriba un "Empezar con: Ideas de clases | Mi propia lista" (`ORIGENES_CLASES`, mismo formato que el de turnos; cambiarlo reinicia lo elegido): con ideas, tarjetas tildables (Yoga · Pilates · Funcional · Taller) bajo "¿Das alguna más?"; con la lista propia no hay ninguna armada, sólo las que se escriben, y cada una se quita con un tachito. Una clase elegida muestra en su encabezado duración (select sobre `DURACIONES`), "Entran [n] personas" (un solo campo) y precio, y debajo "¿Cuándo es?" con `HorariosGrupales`: un horario por fila ("Lun, mié y vie · 18:00 ›") y "+ Agregar horario"; los días (chips Lun…Dom) y la hora (`<input type="time">`) aparecen sólo al editar un horario: hoja que sube desde abajo en el celular, desplegado en el lugar de la fila desde `md`. Un horario cerrado sin días se borra (`limpiarBloquesVacios`); lo que le falta a una clase se dice debajo de ella, y el pie dice "Falta completar X". Cada día de cada bloque es un horario (`horariosDeClase`), el cupo es `capacidad`, y `payload()` manda los turnos individuales y las clases juntos en `tiposEvento`, cada uno sólo si su paso está en el recorrido. Ahí `ListaEventos` va con `conModalidad={false}`: sólo turnos individuales. En `/reuniones`, en cambio, cada fila tiene siempre a la vista un selector "Individual | Grupal" (`SelectorModalidad` en `controles.tsx`, `elegirModalidad` en el hook; en un tipo sin tildar no hay ninguna marcada y elegir una lo activa). Grupal es `TipoEvento.capacidad` (entero 1–100) más sus `horarios` fijos (`[{ dia: 'lun'…'dom', hora }]`), también dentro del Json; el panel de debajo de la fila (`PanelGrupal`) pide los dos — la capacidad en un campo y los horarios con `HorariosGrupales` (`components/onboarding/HorariosGrupales.tsx`), el mismo editor de filas + hoja/desplegado del paso de clases, sobre bloques de días con una hora (`BloqueClase`, `horariosDeBloques`/`bloquesDeHorarios` en `lib/turnos-grupales.ts`; `DatosEvento.bloques` es sólo de pantalla) —, `problemaGrupal` (`web/src/lib/turnos-grupales.ts`, copia a mano de `normalizarTipoEvento` en `api/src/agents/turnos-grupales.ts`) traba el avance del wizard y el "Guardar" de `/reuniones` mientras falte algo, y la API responde 400 con el motivo. Ver "Turnos grupales" más abajo. Titular and bot names need 2+ characters, the DTOs' minimum. State, steps and catalogs live in `web/src/app/contanos/useOnboarding.ts`. `WizardContanos.tsx` renders it as **one responsive DOM** (no separate desktop/mobile layouts): on desktop a step rail on the left (done steps show their answer and are clickable) and, from `lg`, a live chat preview on the right (`VistaPreviaChat.tsx`, built from what was typed); on mobile one step per screen with a segmented progress bar, a back arrow, a sticky bottom button and the preview folded in a `<details>` (open on the last step). The controls live in `controles.tsx`, the ones for tipos de evento shared with `/reuniones`. Its last button `POST`s the fields to `/agents/generate` (`api/src/agents/`), or `nombreTitular` + `nombreBot` + `local` + datos del cliente to `/agents/generate-ventas` for a sales account, which derives `Agent.descripcion` from them (`construirDescripcion`), generates and persists the user's `Agent` (system prompt + allowed actions) before navigating to `/listo`, the screen that announces the free month, and from there to `/vincular`, the WhatsApp QR-linking screen. An account that already scanned (`yaVinculoWhatsapp`, `web/src/lib/session.tsx`: `phoneNumber !== null`) never sees "Vincular WhatsApp": the wizard's last button says "Crear mi asistente" and `/listo` offers "Ir a mi agenda" (`/inicio`) and "Ver planes" (`/plan`). Después del onboarding los tipos de evento se editan en `/reuniones` (`PUT /agents/me/tipos-evento`, `AgentsService.actualizarTiposEvento`): reemplaza la lista y regenera `systemPrompt`/`descripcion` con la plantilla desde el resto de la fila; no toca horarios, nombres ni turnos ya agendados, y el runtime lo ve en el mensaje siguiente porque lee el `Agent` en cada turno. Nothing exists after linking — the "Ir a mi agenda" button just restarts the demo.

**Two doors in: Google or WhatsApp only.** `User.googleId`, `User.email` and `User.phoneNumber` are all optional; `User.calendario` (`"google" | "local"`) says where the agenda lives, and it is explicit on purpose — a Google user who lost the refresh token must fail loudly, not silently fall into the local agenda. A user with neither `googleId` nor `phoneNumber` is a WhatsApp signup that hasn't scanned yet (`esAltaPendiente`, `whatsapp.service.ts`).

- **Signup** (`api/src/auth/whatsapp-auth.controller.ts`, `alta-whatsapp.service.ts`): `POST /auth/whatsapp/alta` is public — it creates the pending user (`calendario: 'local'`), sets a 15-minute `trato_alta` cookie (a JWT with `tipo: 'alta'`, `cookies-de-paso.ts`) and starts the same Baileys pairing `/vincular` uses. `GET /auth/whatsapp/alta/stream` is that SSE, guarded by `AltaGuard`. After `connected`, `POST /auth/whatsapp/alta/finalizar` swaps the alta cookie for `trato_session` and answers `{ destino }`. If the scanned number already belongs to an account, that is a login, not an error: `WhatsappService.transferirSesion` moves the fresh pairing to the existing account (order matters because `saveCreds` writes by `userId`: wait for pending saves, `end()` the new socket without logout, `logout()` the old one after removing it from the map, wait for both sides' saves again, copy creds and key rows in one transaction (`copiarSesion`), reconnect) and the pending user is deleted. Because the endpoint opens sockets, `AltaWhatsappService` caps concurrent signups (20) and per-IP starts (5/hour) with the in-memory `Limitador` (`auth/limitador.ts`, fine only because of the single replica), and discards an abandoned signup when its cookie expires; `RetentionService` purges any left over after a restart (`HORAS_ALTA_PENDIENTE`). `main.ts` sets `trust proxy` so `req.ip` is the client, not Railway's proxy.
- **Password step**: right after the QR, a WhatsApp-only account chooses a password (`/contrasena`). `destinoTrasLogin` (`auth/sesion.ts`) sends any account with `debePonerPassword` (no `googleId`, has `phoneNumber`, no `User.passwordHash`) there before anything else, so `finalizar` lands on it; if the tab is closed first, `/entrar` redirects there and `/inicio` shows a banner. `POST /auth/password { nueva, actual? }` sets it without `actual` only when there is none yet, and answers 403 (not 401, the session is fine) on a wrong `actual`. Hashes are scrypt from `node:crypto` (`auth/password.ts`, `scrypt$N$r$p$salt$hash`, no dependency); `UsuarioPublico` exposes only `tienePassword`/`debePonerPassword`. Google accounts don't use passwords.
- **Coming back** (`login-whatsapp.service.ts`): `/entrar` leads with the phone + password form, `POST /auth/whatsapp/login`. Same 401 for wrong password, unknown number or account without password, and scrypt always runs (against `HASH_FALSO` when there's nothing to compare) so timing doesn't reveal which numbers exist. 10 attempts per number every 15 minutes, 30 per IP per hour in production. The number is **not** matched exactly: `api/src/auth/telefono.ts` holds it as pure functions — `variantesDeTelefono` expands what was typed into the equivalent ways of writing the same number (Argentina's `9` and Mexico's `1` after the country code, a leading `0`, the legacy `15`) and `buscarUsuarioPorTelefono` looks them all up in **one** query, because a loop with an early return would let timing say which form exists. `claveDeTelefono` collapses them into a single stable key, and that — never the typed string — is what every per-number `Limitador` and the dev last-code map are keyed by, so the allowed attempts don't multiply by the ways of spelling the number. What Baileys writes into `User.phoneNumber` doesn't change. On the web the number is never one free-text field: `CampoTelefono` (`web/src/components/ui/CampoTelefono.tsx`, country list in `web/src/lib/telefono.ts`) pairs a country `<select>` with the national number, and `/entrar` and `/entrar/codigo` both use it.
- **Recovery** (`codigo-acceso.service.ts`, `/entrar/codigo`): `POST /auth/whatsapp/codigo` sends a 6-digit code to the owner's own chat (`WhatsappService.enviarAlPropioChat`; `handleMessagesUpsert` already ignores `fromMe`, so the bot never answers it). It always answers 202 and does the work in the background so neither the status nor the timing reveals whether the number has an account. Only a SHA-256 of the code is stored (`CodigoAcceso`), 10-minute expiry, 5 attempts, single use, plus per-number and per-IP limits. `POST /auth/whatsapp/codigo/verificar` requires `nuevaPassword`, stores it and sets the session — that is also how accounts created before passwords existed get one. With no live socket there's nothing to send through; the web tells the user to scan the QR again, which lands in the same account thanks to the transfer above.
- **Phone as identity for everyone**: on `connection: 'open'` `WhatsappService.asignarTelefono` stores the number in `User.phoneNumber`, so Google accounts can log in by code too. If the number already belongs to another account and this isn't a pending signup (a Google owner linking someone else's WhatsApp), the SSE gets `{ state: 'error', motivo: 'numero_en_uso' }` and the session is logged out. `handleConnectionUpdate` ignores events from any socket that is no longer the one in `sockets` for that user — that is what keeps a transferred or discarded socket's `loggedOut` from deleting the row that was just written.
- **The local agenda** is `CalendarioLocal` (`api/src/calendar/calendario-local.ts`) over the `Evento` table, with the exact contract of the Google calls. `CalendarService` routes by `user.calendario`, so the graph, the Home test bench and `/calendario` don't know which one they're on; `Turno.googleEventId` keeps its name and holds an `Evento.id` for local accounts. `POST /calendar/eventos` (the "Nuevo evento" button in `/calendario`) exists because a local account has no other way to block time.
- **Connecting Google later**: `/cuenta` sends a local account to `GET /auth/google/conectar`, which sets a short `trato_conectar` cookie and goes to the normal consent. `GoogleStrategy` (`passReqToCallback`) sees that cookie and, only if it matches the live session's user, calls `AuthService.conectarGoogle` instead of the login upsert (409 if the Google account is someone else's; the Google email is adopted only if the account had none and nobody else uses it). `GoogleAuthGuard.handleRequest` puts the outcome on the request, and the callback runs `CalendarService.migrarLocalAGoogle`: event by event it creates in Google, repoints the `Turno`, then deletes the local row, so a failure halfway loses nothing. `calendario` flips to `google` only when nothing is left, and the browser lands on `/cuenta?google=conectado|google_en_uso|migracion_incompleta`.
- **Paying without an email**: Mercado Pago needs `payer_email`, so `POST /suscripcion/checkout` takes an optional `email` (`CheckoutDto`), required only when `User.email` is null; it is stored on the user (409 if another account has it). `/plan` shows the field only then.

**It must not read like a bot.** That is the product, so it lives in code on both ends. On the WhatsApp side (`api/src/whatsapp/`), `handleMessagesUpsert` doesn't answer message by message: it puts each one in `AgrupadorDeRafagas` (`agrupador-rafagas.ts`), which waits `ESPERA_RAFAGA_MS` (6 s) of silence — capped at `MAXIMO_RAFAGA_MS` (20 s) from the first message — and hands the whole burst to the graph as one text joined by `\n`; it also serializes per chat, so what arrives while a reply is going out waits for it (before, two quick messages ran the graph in parallel on the same thread). A burst is capped at `MAX_MENSAJES_RAFAGA` (20) messages / `MAX_CARACTERES_RAFAGA` (4000) characters, each message truncated to that: a full burst is answered right away and the overflow that arrives while it's being answered is dropped, so a spamming client can't grow memory or the owner's model bill. `cerrarSocket` discards a user's pending bursts. It can't know when the client is typing: WhatsApp only delivers `chatstate` ("escribiendo…") to devices that are online, and the socket connects as unavailable (`markOnlineOnConnect: false`, see "WhatsApp connection") because online the owner's phone stops ringing — so the silence wait is long instead (`presenceSubscribe`/`presence.update` were tried and never fired). If the client sends another message while a reply is being built, the reply is **discarded and redone with everything together**: each run gets a `Cancelacion` (`src/conversation/cancelacion.ts`) whose signal reaches `graph.invoke` and the LLM call; the nodes with side effects call `comprometer()` first (`catalogo` before `crear_pedido`/`cancelar_pedido`/`derivar_consulta`, `calendar` before writing a turno or event, `persistir` at its start), and after that the run can't be cancelled — the reply goes out and the new message waits for it. A cancelled run makes `ConversationService.responder` throw `VueltaCancelada` and remember the checkpoint from before it (`vueltasDescartadas`); the retry invokes with that `checkpoint_id`, so LangGraph forks from there and the half-done turn (the client's message, a search) isn't counted twice — with an empty thread before, it `deleteThread`s and seeds again from `Message`, which the discarded run never wrote. At most `MAX_CANCELACIONES_POR_RAFAGA` (2) discards per burst, since each one is a model call the owner pays. The agrupador re-queues the items at the front of the burst. In memory, so single replica only, like the sockets. `contestarRafaga` then marks the burst read, shows "escribiendo…" (renewed every `RENOVAR_ESCRIBIENDO_MS`) while the model runs, and sends the reply split by `partirEnMensajes` (one message per blank-line block, at most `MAX_PARTES` 3), each after `demoraDeEscritura` — the model's own latency counts toward the first one. All of that is pure in `ritmo-humano.ts`; read/presence failures never block the reply, and with the subscription expired nothing is marked read. The Home test bench splits the reply the same way (hand copy in `TestChat.tsx`). On the prompt side, `reglasDeNaturalidad` (`api/src/conversation/graph/naturalidad.ts`, shared by both graphs, appended after the style block) bans call-center phrases (`FRASES_DE_ROBOT`), asks it to match the client's register and never mention tools or internals, tells it a blank line splits messages, and holds the identity rule the owner chose: it doesn't introduce itself as a bot or AI, but if a client sincerely asks whether it's a person it never denies being automatic and offers the owner (`derivar_consulta` in ventas; in agenda the owner reads the same chat). The style blocks no longer carry a fixed confirmation format or an emoji-per-line legend. In ventas, when an emoji goes is decided in code, not by the model (left alone it almost never used one): `pistaDeEmoji` (`naturalidad.ts`) looks at the assistant's last replies and adds "none in this one" right after one with an emoji, or "add one" after `MENSAJES_SIN_EMOJI` (2) without — about one every three messages, at most one per message. `PLANTILLA_VERSION` 6 / `PLANTILLA_VENTAS_VERSION` 7 carry the same tone (agenda's 6 only adds the group turnos to the tipo list) ("atendés el WhatsApp de …"); the sales assistant talks as part of the team, in first person plural ("tenemos", "te escribimos por acá"), never about the shop in third person — `REGLA_VOZ_DE_EQUIPO` in `reglasDeVenta` says so in code and every tool result and rule that used to say "{titular} te responde / lo coordina" now says "le escribimos por este chat".

**The WhatsApp conversation is a LangGraph graph, not a script.** `WhatsappService.handleMessagesUpsert` (`api/src/whatsapp/whatsapp.service.ts`) listens to Baileys' `messages.upsert`, ignores group chats and the owner's own messages, and hands each burst of text messages (see above) to `ConversationService.responder` (`api/src/conversation/conversation.service.ts`), now a thin facade that resolves the owner's `Agent` and invokes the compiled graph with `thread_id = Conversation.id`. The graph (`api/src/conversation/graph/`) has one LLM node and four code nodes:

```
START -> cargar_contexto -> conversacion --sin tool calls--> persistir -> END
                                 ^              |
                                 |          (tool calls)
                                 |              v
                              calendar <--ok-- validacion
                                 |              |
                                 +--------------+ (rechazo: vuelve sin tocar Google)
```

- **`cargar_contexto`** (code) loads the `Agent` (+`user`), the `Conversation`, the active `Turno`, and calls `freeBusy` **once** over the next `DIAS_VENTANA` (14) days, merging into it the owner's own confirmed `Turno` rows (`unirOcupados`) — a free DB read that covers what `freeBusy` hasn't propagated yet and events the owner marked "Disponible", which `freeBusy` never reports as busy. It turns that into a compact per-day list of free gaps that goes straight into the system prompt, alongside the generated `systemPrompt`, the hard-rules block, the scope block and the style block (`reglasDeAgenda` / `reglasDeAlcance` / `reglasDeEstilo`), the first two built from the `Agent` row. Only `DIAS_RESUMEN` (5) working days of that window reach the prompt — weekends are skipped entirely, not printed as "sin huecos". That snapshot is why a whole conversation costs one Google read instead of one per tool call.
- The **owner's own tools** (`ESQUEMAS_PROPIETARIO`, `conversation-tools.ts`) are bound only when the message comes from the Home test bench. `listar_turnos` is the one that reads the `Turno` table across every conversation, with each client's name — `consultar_turno` is scoped to the conversation in hand, which in the test bench is empty, so without it the owner asking "what do I have tomorrow?" got nothing. Its companions `listar_eventos_calendario` / `cancelar_evento_calendario` / `editar_evento_calendario` work on the calendar, not on turnos. The same turnos also go into the owner's prompt (`bloqueTurnosDelDueno`, capped at `MAX_TURNOS_EN_PROMPT`), from the read `cargar_contexto` already does, so the common question costs no extra round trip; that block never reaches a client's prompt, where it would be other people's data.
- **`conversacion`** is the only node that calls the model. It binds the tools in `allowedActions` (plus the owner-only ones when the message comes from the Home test bench) as zod schemas — `api/src/conversation/conversation-tools.ts` now holds only the definitions, no execution. It never sends the whole thread: only `mensajesVisibles(state.messages, state.inicioVisible)` (see "History window" below).
- **`validacion`** (code) checks each tool call against the snapshot and rejects with a `ToolMessage` without touching Google. Within one `AIMessage` it accumulates the ranges it already approved (`provisorios`), so two `crear_turno` in the same model response cannot both be measured against the same stale photo and end up overlapping. It also answers `consultar_disponibilidad` straight from the snapshot whenever the range falls inside the preloaded window.
- **`calendar`** (code) is the only door to Google Calendar and the `Turno` rows; it runs just what validation approved and updates the in-memory snapshot so the rest of the turn stays consistent. Before writing a `crear_turno` or `reprogramar_turno` it re-reads that one range in Google (`choqueDeUltimoMomento`) — a small `freeBusy` per booked turno, not per message — and aborts without writing if something got in between the snapshot and now (a parallel conversation, or the owner adding an event by hand). That is the last barrier against double-booking; the rules themselves still live in `agenda-rules.ts`.
- **`persistir`** mirrors the turn into the `Message` table in the same OpenAI-shaped JSON as before, and recomputes `Conversation.resumen` only every `CADA_CUANTOS_MENSAJES_RESUMIR` (6) messages, since that is a second model call.

**History window** (`api/src/conversation/graph/ventana-historial.ts`, pure, shared by both graphs). The model only sees the part of a chat that arrived within `HISTORIAL_IA_VENTANA` (env, `<n>m|h|d`, default `14d`, parsed by `parsearDuracion` in `config/env.ts` into `HISTORIAL_IA_VENTANA_MS`; set it short in develop). Nothing is deleted — `Message` and the checkpointer keep everything until the usual retention; it only stops being sent. Each `cargar_contexto` calls `prepararHistorial`: it stamps the incoming `HumanMessage` with `response_metadata.recibidoEn` (replaced in place by id; `@langchain/openai` never sends `response_metadata`, and it survives the checkpointer), and computes `inicioVisible`, the first client message inside the window — always cutting at a client message, so a tool call is never split from its result, and never past the message that just arrived. Messages without a stamp (everything before this change) count as old. `sinParesCortados` (also what `mensajesDesdeFilas` uses when seeding) drops any `AIMessage` whose tool calls have no `ToolMessage` and orphan results: a turn cut halfway (e.g. `GraphRecursionError`) used to leave such a pair and the provider then rejected every following message of that chat (Sentry TRATO-API-3). When part of the thread is outside the window (`hayHistorialOculto`), `Conversation.resumen` is hidden too (the `contexto.conversation` copy gets `resumen: null`, so `persistir` rebuilds it without the old one); `nombreCliente` is kept. `yaSePresento`, Jev's `mensajesDelCliente` and the seeding from `Message` (`ConversationService.historialSemilla`, filtered by `createdAt`) all use the window too. The graph factories take `ventanaHistorialMs` as an optional dep (default 14 days) so tests and evals don't have to pass it; production wires it from `ConfigService` in `conversation.providers.ts`.

Conversation state lives in a `PostgresSaver` checkpointer (`checkpointer.provider.ts`). Its tables (`checkpoints`, `checkpoint_writes`, `checkpoint_blobs`, `checkpoint_migrations`) are created by `setup()` at boot and are **outside** the Prisma migrations on purpose — `prisma migrate reset` wipes them. When that happens with the API already up, the saver recreates them by itself: `SaverAutoReparable` (same file) catches Postgres' `42P01` on any checkpointer operation, re-runs the idempotent `setup()` once (sharing a single repair across concurrent messages) and retries — no `docker compose restart api` needed. Everything in the graph state except `messages` is an `UntrackedValue`, so the owner's Google refresh token never gets serialized into a checkpoint. Threads created before the migration are seeded once from the `Message` table (`graph/historial.ts`).

The four agenda rules — weekdays only, no overlapping, at least `MARGEN_MINIMO_MIN` (5) minutes between turnos, and always asking the client's name — live in `graph/agenda-rules.ts` as pure functions and are enforced by the `validacion` node, not only by the generated prompt: `crear_turno` requires a `nombreCliente`, both it and `reprogramar_turno` reject anything outside the `Agent`'s `horaDesde`/`horaHasta` or falling on a Saturday or Sunday (`esDiaHabil`, the `DIAS_HABILES` set — deliberately a constant and not an `Agent` column, so it applies to already-generated agents with no migration), and collisions are checked over the range widened by the margin (`conMargen`). `huecosDelDia` returns nothing for a non-working day, which is the single choke point that keeps weekends out of the prompt summary, out of `horariosCercanos` suggestions and out of the day pool. A collision rejection carries the fix, not just the refusal: `mensajeOcupado` appends the nearest free slot found by `horariosCercanos`, which walks the loaded window through `huecosDelDia` and picks, inside each gap, the point closest to what was asked (asking for 10:03 right after a turno ending at 10:00 suggests 10:05, not the 09:00 start of the gap). `parsearFecha` anchors any ISO string without an offset to `TIMEZONE` before `new Date`: the API container runs in UTC, so "14:00" used to become 11:00 ART and every collision check ran against the wrong instant. `reprogramar_turno` filters the turno's own event out of the busy periods (`conflictos`), otherwise the margin makes a small move collide with itself. The rules block in the system prompt is built from the `Agent` row (not from the generated prompt, so it survives regeneration), and `Conversation.nombreCliente` is reused so the agent doesn't ask for the name twice. There is **no confirmation step**: once the client picked a free time and the bot knows the name and tipo de turno, `reglasDeAgenda` has it call `crear_turno` in that same answer and tell the client it's booked; a move or cancellation is done as soon as it's asked (people didn't answer "¿te lo confirmo?"). The template says the same since `PLANTILLA_VERSION` 4, so the boot regeneration rewrote every saved agent. Only the owner's `cancelar_evento_calendario` / `editar_evento_calendario` (any calendar event, not a turno) still require `confirmado: true`. `reglasDeAlcance` (same file, same reason it lives in code) is what keeps the agent on topic: it may only talk about turnos and the business data already in the `Agent` row (attention window, tipos de turno, who attends), it must refuse anything else in one line — including an off-topic question smuggled into a booking message — and it must never invent business data it wasn't given (prices, address), deferring to the owner instead. The deterministic template (`agent-template.ts`) echoes the same restriction so a freshly generated prompt agrees with it, but the code block is the guarantee and covers agents generated before either of them existed, with no regeneration. `reglasDeEstilo` (in `cargar-contexto.node.ts`, same reasoning) is the third code-owned block: short answers in WhatsApp's own formatting rather than markdown (single-asterisk bold, one option per line with `* `, at most 2 emojis per message), never more than `MAX_OPCIONES_DIA` (3) times per message; `reglasDeEstiloVentas` (`ventas/reglas-ventas.ts`) is its sales twin, capped at `MAX_PRODUCTOS_POR_MENSAJE` (3) products (`ver_catalogo` aside). The validation node pushes the same way — a single-day `consultar_disponibilidad` (`esConsultaDeUnDia`) is answered with `resumenDelDia` instead of the busy-period dump: a free day comes back as a range ("libre de 09:00 a 18:00"), a day that already has turnos comes back as up to three spread-out times from `opcionesDelDia` plus the instruction to ask "¿mañana o tarde?" first. A `CalendarUnavailableError` (revoked/missing token, Google API failure) turns into an apology instead of crashing the graph; if it happens while loading the snapshot, the validation node refuses to book anything. `LIMITE_RECURSION` (14 supersteps) replaces the old 4-round-trip cap.

**Lugar de atención (LAU-17).** The agenda assistant knows where the turnos happen, configured like the sales local and stored in the same `Agent.local` Json (no migration): `normalizarLocal(entrada, 'agenda')` keeps `tieneLocal`, `lugar` (`TIPOS_LUGAR`: `local` | `casa`), a **required** `direccion` and an optional https `enlaceUbicacion`, and drops `horarios`/`retiroEnLocal` (the franja and the classes already say when); `tieneLocal: false` is "no tengo un lugar fijo" (online or a domicilio); `null` is never filled in (every agent before this, which keep the old "no sabés la dirección" behaviour). `leerLocal(agent, tipo)` reads it per type, and ventas drops `lugar`. It's asked in the wizard step "¿Dónde atendés?" right after "¿Cómo atendés?" (`ControlesLugar.tsx`: three cards like `ElegirAtencion` — En un local o consultorio · En mi casa · No tengo un lugar fijo — plus `CamposDireccion`, shared with `ControlesLocal`; its own `useLocal(null, { paraAgenda: true })` instance, preselected local, blocked until there's an address), sent as `local` in `POST /agents/generate` (absent leaves what was saved, like ventas), and edited in the "Dónde atendés" section of `/cuenta` (`SeccionLocal` with `tipoAsistente`, same `PUT /agents/me/local`). The prompt side is pure, in `api/src/conversation/graph/lugar.ts`: `bloqueLugar` (added after `reglasDeAgenda` in both the owner's and the client's context; address with `JSON.stringify`) and `reglasDeAlcance`, which stops listing the address as unknown once a place is loaded. **A home address is gated in code**: for a `casa`, the client's prompt doesn't contain the address until the conversation has a confirmed turno (`turnoActivo`) — the owner always sees it. Since the prompt is built before the booking, the `calendar` node appends `lineaDeLugarParaTurno` (place + address + map link) to every successful `crear_turno`/`reprogramar_turno` result (`Efecto.conTurno`), which is how the client gets the address in the same message that confirms the booking, for a local too. The e2e stub answers "dónde"/"dirección" from that block and, after a tool, echoes its result, so the "Lugar: …" line reaches the reply (`e2e/tests/lugar-atencion.spec.ts`).

**Turnos grupales (LAU-13).** A tipo de turno with `capacidad` + `horarios` is a group class: several clients book the same fixed slot until it's full. The owner's schedule is the rule, so weekdays-only and the franja don't apply to it (they're still the rule for individual turnos). Pure rules in two files: `api/src/agents/turnos-grupales.ts` (validation/normalization for the DTO path, `leerGrupal` for reading the Json — malformed means individual, never an invented capacity — and the prompt text `detalleGrupal`, which `detalleDeTipo` appends after duration and price so the e2e stub's regex still reads the duration) and `api/src/conversation/graph/turnos-grupales.ts` (a "clase" is one occurrence of a fixed slot in the loaded window: `clasesEnRango`, `tipoPorNombre` matching the tool call's `resumen` without case/accents, seat counting by `claveClase`). `cargar_contexto` merges every class in the window into the busy periods — even with nobody booked, so no individual turno lands on one — and adds `bloqueTurnosGrupales` (next classes per tipo with seats left, counts only, never other clients' names). `crear_turno` for a group tipo skips `chequearHorario`: `validacion` only accepts the exact start of a real class, rejects a full one or a conversation already in it (counting approvals in the same model message), and takes the class's `fin`, not the model's. Only group bookings set `Turno.tipo` (migration `turno_tipo`; null = individual); everyone in a class shares one calendar event titled `Yoga (grupal) · 3/10` (`tituloEventoGrupal`, no names). `CalendarService.inscribirEnTurnoGrupal` recounts inside a transaction holding `pg_advisory_xact_lock` per owner+tipo+start (the race for the last seat; `turnos-grupales.db.spec.ts` covers it against real Postgres), creates the event only for the first one, and `bajaDeTurnoGrupal` deletes it only when the last one leaves (inside the transaction, so a Google failure leaves the turno confirmed). Rescheduling a group turno books the new class first and then drops the old seat. If the owner later turns a group tipo back into an individual one, existing bookings keep their shared event until cancelled; rescheduling them is refused (cancel and book again).

**The commerce module (asistente de ventas).** `Agent.tipoAsistente` (`"agenda"` default | `"ventas"`) is the discriminator, **not** `tipoUso`: saved agents with `tipoUso: 'comercio'` are agenda bots and stay that way. An account never switches type (`AgentsService.exigirMismoTipo` → 409). `POST /agents/generate-ventas` takes only `nombreTitular` + `nombreBot` (the bot works 24/7, no franja) and uses its own deterministic template (`agent-template-ventas.ts`); `UsuarioPublico.tipoAsistente` drives the nav (`pestanasDe` in `AppHeader.tsx`, `ITEMS_VENTAS` in `MobileTabBar.tsx`: Inicio, Productos, Ventas, Chat) and `/reuniones` bounces a sales account to `/productos`.

- **Stock y a medida en la misma cuenta** (LAU-21 dejó de ser de la cuenta): no hay `Agent.modalidadVenta` ni `Agent.queHace` (migración `sin_modalidad_venta`), ni paso "Cómo vendés"/"Qué hacés" en `/contanos`, ni sección en `/cuenta`, ni `UsuarioPublico.modalidadVenta`. **Lo decide cada producto**: con `Producto.solicitud` (aunque sea `{ preguntas: [] }`, leída con `leerSolicitud`) es a medida; sin ella, de stock. En el grafo de ventas, `cargar_contexto` cuenta en el mismo `Promise.all` los productos activos con `solicitud` y deja `ContextoVentas.tieneAMedida` (también true si la charla ya tiene un pedido a medida; `pedidosAMedida` se carga siempre). Con eso: `reglasDeVenta(agent, mp, etapa, aMedida)` mantiene las reglas de stock (con "Para vender un producto con stock" y "los a medida no tienen stock") y suma `reglasAMedida` (encabezada por `MARCA_A_MEDIDA` = `Productos a medida (se cotizan)`, que lee el stub de e2e: `REGLA_A_MEDIDA`, precio de referencia, versiones fijas → `pedir_variante`, cambios → `registrar_solicitud`, `REGLA_FOTOS_A_MEDIDA`, preguntas en orden, `aceptar_presupuesto`, `derivar_a_persona`); `bloquePedidos` suma el cobro de presupuestos y la lista de pedidos a medida; `reglasDeAlcanceVentas` y `naturalidadVentas` nombran los dos caminos; `accionesDeVentas(allowedActions, { aMedida })` deja siempre `crear_pedido`/`cancelar_pedido` y suma `registrar_solicitud`, `pedir_variante`, `aceptar_presupuesto`, `derivar_a_persona` sólo con `aMedida` (el nodo `conversacion` le pasa el `contexto` a `herramientas`). The description is for the bot to understand the product, not to recite (`reglasDeVenta` says so). - **Search** (`busqueda.service.ts`): reciprocal rank fusion (`RRF_K` 60) of four candidate lists — exact code/SKU, Spanish full-text (`consultaTsquery`: OR of words, prefix match except numbers), trigram `word_similarity` (≥ 0.5, words ≥ 4 chars) and exact cosine distance in pgvector filtered by `userId` (≤ `DISTANCIA_MAXIMA` 0.7, calibrated against the real model). There is deliberately **no HNSW index**: a global approximate index filtered per tenant returns too few rows. `textoBusqueda` is normalized in code (no `unaccent`); `busqueda` (tsvector) and `embedding` are `Unsupported` columns written with raw SQL, with their GIN indexes declared in the schema so Prisma doesn't try to drop them. `IndexadorService` embeds products whose `embeddingHash` ≠ `md5(textoBusqueda)` (after each write, plus a 10-minute sweep) through `embeddings.client.ts` — OpenRouter `/embeddings`, `OPENROUTER_EMBEDDINGS_MODEL` (default `openai/text-embedding-3-small`, 1536 dims), with `POLITICA_DE_PROVEEDOR` because the search text is client conversation. A product without an embedding is still found by text; if the query embedding fails, search degrades to text only.

- **The sales graph** (`api/src/conversation/ventas/`) mirrors the agenda one: `cargar_contexto → conversacion → validacion → catalogo → conversacion … → verificar_respuesta → persistir`, reusing `conversacion` and `persistir` (their state type is `EstadoComun`). `ConversationService` picks the graph by `tipoAsistenteDe(agent)` and gives it `LIMITE_RECURSION_VENTAS` (the agenda limit + 4, for the extra node and one correction round). - **Discounts** (`descuentos.rules.ts` pure, `Descuento` table, LAU-8): percentage (1–`PORCENTAJE_MAX` 90) or fixed amount in cents, with optional `desde`/`hasta` days (stored as `[inicio del día, inicio del día siguiente)` in `TIMEZONE`) and an `activo` switch. The scope comes from the row: `productoId` = the product's own discount (one per product, saved inside `GuardarProductoDto.descuento` — `null` deletes it, absent leaves it alone so the CSV import never touches it); `categoria` = a category promo; neither = whole catalog. Promos (`/descuentos`, `DescuentosController`, max `MAX_PROMOCIONES` 20, every query scoped by `userId` and `productoId: null`) live in the "Promociones" panel of `/productos`. `mejorDescuento` picks the one that saves the client the most (ties: product > category > catalog > id) and **never stacks**; a discount that would leave the price at ≤ $0 doesn't apply. It's applied in code everywhere the price shows up: `BusquedaService.cargar` (`precioFinalCentavos` + `descuento` on each `VarianteEncontrada`), `SugerenciasService.panorama` ("desde" on final prices), `aProductoPublico` and `VentasService.reservar`, which reads the discounts inside the reservation transaction and stores `precioUnitarioCentavos` **already discounted** plus `precioListaCentavos`/`descuentoCentavos`/`descuentoEtiqueta` on `ItemVenta` — so totals, Mercado Pago's `unit_price`, `pagoSaldaVenta`, history and CSV need nothing new. The bot also brings them up on its own: the first `buscar_productos` with results or `ver_catalogo` with something in stock in a conversation gets `conOfertaDeDescuentos` appended when the account has any discount a client can use (`SugerenciasService.descuentosVigentes`, which counts active rows first and skips the catalog read when there are none), telling the model to offer them in one line without adding a second question. It happens **once per conversation**: the `OFERTA_DE_DESCUENTOS` marker stays in that ToolMessage in the checkpoint, and `yaSeHablaronDescuentos` (by content, not tool name, and only over tool messages, so a client can't switch it off) also counts a past `ver_descuentos`. The form's live preview (`web/src/lib/descuentos.ts`) is a hand copy of `montoDeDescuento`; the API's number is the one charged. `/productos` is two columns from `lg` (catalog left; "Probá qué encuentra tu asistente" and "Promociones" in a sticky aside), and the product grid and each card use container queries (`@container`, `@xl:`/`@5xl:` on the list, `@md:` inside the card) so they adapt to the column's width, not the viewport.

**The free month is a rule, not a row.** Every user gets `DIAS_PRUEBA` (30) days of everything, counted from `User.createdAt` — the Google login — with no card asked for. `api/src/subscription/subscription.rules.ts` holds that as pure functions (`finDePrueba`, `estadoDeSuscripcion`), the same way `agenda-rules.ts` holds the agenda rules: deriving the trial instead of storing it means users created before billing existed need no backfill, and `estado` (`activa | prueba | por_vencer | vencida`, the last two split at `DIAS_AVISO` = 7) is computed the same way everywhere. A `Subscription` row only appears once a payment starts. The trial can't be restarted by deleting the account and signing up again: `CuentaService.eliminar` first leaves a `PruebaConsumida` tombstone per identity (HMAC of googleId/phone, and of the email only on Google accounts — a WhatsApp account's email is typed at checkout and unverified, so it could burn a third party's trial — with a subkey of `TOKEN_ENCRYPTION_KEY`, plus the original `createdAt`; `subscription/prueba-consumida.ts`, never purged on purpose, no FK to `User`), and `SubscriptionService.resolver` starts the trial at the oldest of `createdAt` and the tombstones matching the user's current identities. It is read-time so it covers Google, WhatsApp signup and connecting Google later. `/privacidad` says it. The price is `SUSCRIPCION_PRECIO_ARS` and nothing else: the landing reads it from the public `GET /suscripcion/precio` (client-side, `PrecioPlan.tsx`, because inside compose the Next server can't reach `NEXT_PUBLIC_API_URL`), and `SuscripcionPublica.monto` returns the row's `montoCentavos` only while the subscription is `activa` — a pending or cancelled row may hold an old price, and the next checkout charges the env one. No screen hardcodes a fallback number.

**Two plans: Básico and Pro.** `PLANES` (`subscription.rules.ts`) holds both: Básico up to 2.500 chats per month at `SUSCRIPCION_PRECIO_ARS`, Pro up to 6.000 at `SUSCRIPCION_PRECIO_PRO_ARS` (default 59000). `Subscription.plan` (`basico` default — rows from before the tiers paid the Básico) is set by `POST /suscripcion/checkout { plan }`, and `GET /suscripcion/precio` returns `{ moneda, planes: [{ id, nombre, chats, monto }] }`, which the landing and `/plan` render (no hardcoded numbers). Switching plan while `activa` leaves the live row untouched: the new preapproval is stored as `mpPreapprovalPendienteId` + `planPendiente`, and only when the webhook reports it `authorized` does `resolverCambioDePlan` adopt it (plan, amount) and cancel the old one in Mercado Pago — abandoning the payment loses nothing, and `sincronizarDesdeMp` ignores events of a preapproval that is no longer the live one (the old one's `cancelled` can't overwrite the new). A **chat** is a distinct `Conversation` with at least one inbound (`role = 'user'`) `Message` in the calendar month in `TIMEZONE` (`rangoDelMes`, `SubscriptionService.chatsDelMes`; the owner's `web-test:` chat doesn't count). The limit is **informational, never a cut**: `estadoDeCupo` flags `cercano` (≥ 80 %) and `superado` (≥ 100 %), `SubscriptionService.avisarSiLlegaAlTope` runs after each answered burst in `contestarRafaga` (fire-and-forget, errors to `logger.error`) and creates one `cupo_chats` notification per month and threshold (`clave` `cupo_chats:80|100:AAAA-MM`, checked even if already read), and `GET /suscripcion` exposes `plan` and `uso { chats, limite }`. During the free month the displayed limit is the Pro's.

When the month runs out and nobody paid, **only the WhatsApp assistant goes quiet** — the agenda, the calendar and every screen stay open, which is what the copy promises. The cut is `estadoDeSuscripcion(...).asistenteActivo`, checked at the two doors into the graph: `WhatsappService.handleMessagesUpsert` skips the message without answering (the Baileys session stays linked, so paying brings the bot back with no new QR), and `ConversationController.test` — the Home test bench, where the reader is the owner — answers `MENSAJE_SUSCRIPCION_VENCIDA` instead of silence.

Payment is Mercado Pago's `preapproval` API and nothing else: `POST /suscripcion/checkout` creates it with `status: 'pending'` and hands back the `init_point` the browser is redirected to, so no card data ever reaches this codebase. `mercadopago.client.ts` is a `fetch` wrapper shaped exactly like `openrouter.client.ts` (no SDK, no axios). `POST /suscripcion/webhook` is the only unguarded `POST` in the API: it verifies the `x-signature` HMAC (`webhook-signature.ts`, built from headers + the `data.id` query — **not** the raw body, which is why `main.ts` needs no `rawBody`), then ignores the payload's contents and re-reads the preapproval from Mercado Pago before upserting by `mpPreapprovalId`, so repeated deliveries are idempotent. It always answers `200`; a 5xx would put MP into a retry loop.

On the web side `SuscripcionProvider` (`web/src/lib/suscripcion.tsx`) fetches `GET /suscripcion` once per session and is what `AvisoSuscripcion` (banner on `/inicio`, `/calendario`, `/chat`; bottom sheet on mobile when vencida) and `/plan` read. `/plan` redirects to Mercado Pago and comes back at `?volviendo=1`, where it polls `GET /suscripcion` a few times because the webhook can land after the browser does. Note the lint rule the app enforces: `setState` may not be called in an effect body, so both the provider and that polling set state inside promise callbacks.

**Google OAuth verification shapes several of these decisions.** `docs/verificacion-google.md` is the working document: what data the app touches, what reaches the model, the draft reply to Google, the demo-video script and the manual steps left. Two consequences live in the code. `GOOGLE_SCOPES` (`api/src/auth/google.strategy.ts`) must match **exactly** what the Google Cloud consent screen lists — `openid`, `profile`, `email` and `https://www.googleapis.com/auth/calendar`, the only sensitive scope configured there. Requesting one that isn't listed (it happened with `calendar.events` + `calendar.freebusy`) makes Google show the app as unverified and the login fails. The code only touches events on `primary` (`events.insert`/`patch`/`delete`/`list`), so `calendar.events` would technically suffice; switching to it means changing the console and this list together. `CalendarService.freeBusy` keeps its name but reads `events.list` with a narrow `fields` mask instead of `freebusy.query`, and decides what blocks — cancelled, "Disponible"/transparent, `workingLocation` and self-declined events don't, all-day events span midnight to midnight in the calendar's `timeZone` — in the pure `src/calendar/ocupados-google.ts`. Changing the scopes forces every existing user to re-consent; a stale token then yields a 403 that `calendar.service.ts` translates into `GoogleReconsentimientoError` ("log in with Google again") instead of a generic 502. And `DELETE /auth/me` (`api/src/auth/cuenta.service.ts`, surfaced at `/cuenta` in the web app) is a real self-service deletion: it revokes the token at `https://oauth2.googleapis.com/revoke`, cancels Mercado Pago, closes the Baileys session, deletes the LangGraph threads — **they are outside Prisma's cascade**, which is the easy thing to miss — and then deletes the user. Events already written to the owner's calendar are deliberately left alone. `api/src/retention/` holds the retention windows as pure functions the same way `subscription.rules.ts` does (messages and conversation state at 90 days of inactivity, client name and summary at 12 months, turnos for the life of the account), applied by an idempotent daily purge (plus the sales and notification windows described in the commerce module); those numbers are published in `/privacidad`, so changing one means changing the policy too.

**The session lives in a cookie, and the API owns it.** `GET /auth/google/callback` (`api/src/auth/auth.controller.ts`) sets a `httpOnly` JWT cookie named `trato_session`. The frontend can never read it — `SessionProvider` (`web/src/lib/session.tsx`) asks `GET /auth/me` on mount and exposes `status: "loading" | "authenticated" | "anonymous"`. `useRequireSession()` is the route guard (redirects to `/entrar`); `signIn()` is a full-document `window.location` navigation, because `router.push` cannot cross origins. All API calls go through `apiFetch` (`web/src/lib/api.ts`), which sets `credentials: "include"`; CORS on the API side is `origin: FRONTEND_URL, credentials: true`.

The guard is deliberately client-side: verifying the JWT in a Next `proxy.ts` (Next 16's renamed `middleware.ts`) would mean sharing `JWT_SECRET` with the frontend. Do not add one.

**Dev-only password login.** `api/src/auth/dev-auth.controller.ts` (`GET /auth/dev` → `{ habilitado }`, `POST /auth/dev/login` with `{ password, email?, telefono? }`, `GET /auth/dev/ultimo-codigo?telefono=`) issues the same `trato_session` cookie as the Google callback (both read `api/src/auth/cookie.ts`) and answers `{ destino }` instead of redirecting; `LoginDev.tsx` on `/entrar` then does a full `window.location` navigation so `SessionProvider` re-asks `/auth/me`. Three locks keep it out of production: `AuthModule` only registers the controller when `process.env.NODE_ENV !== 'production'`, the handler 404s in production or without `DEV_LOGIN_PASSWORD`, and `validateEnv` refuses to boot if `DEV_LOGIN_PASSWORD` is set in production; the web only mounts the form behind `process.env.NODE_ENV !== "production"`, which is inlined at build time. Dev users get `calendario: 'local'` and no refresh token, so they use the same Postgres agenda as WhatsApp-only accounts (it survives restarts; the old in-memory `CalendarioDev` is gone, and the migration flipped existing `dev:` users to `local`). With an email they get `googleId = 'dev:<email>'` (`api/src/auth/usuario-dev.ts`) and `upsertUsuarioDev` refuses (409) an email that already belongs to a Google user; with a `telefono` they imitate a WhatsApp-only account (no `googleId`) and it refuses a number whose owner has a real registered WhatsApp session. A dev user has no socket to receive a login code, so outside production `CodigoAccesoService` keeps the last code per number and `GET /auth/dev/ultimo-codigo` returns it (same three locks). That is why `CalendarService` methods take `Pick<User, 'id' | 'calendario' | 'googleRefreshToken'>` instead of just the token.

Cookies are not scoped by port, so `:4000` and `:3000` share `localhost` locally. In production front and API are `tratoagenda.com` and `api.tratoagenda.com`, which **are** the same site, so `opcionesDeCookie` (`api/src/auth/cookie.ts`) uses `sameSite: 'lax'` there too — that is what makes the login work on Safari/iOS, which blocks third-party cookies outright. It decides by comparing `FRONTEND_URL` with `GOOGLE_CALLBACK_URL` (the API's own public URL) and demands a real host parent/child relationship, not a shared registrable domain: two sibling `*.up.railway.app` subdomains share `railway.app` but `up.railway.app` is on the Public Suffix List, so they are not the same site and treating them as one would break the login with no visible error. That case falls back to `sameSite: 'none'` + `secure`. Since `none` loses the browser's CSRF guard, and the rule costs nothing anyway, `main.ts` mounts `chequeoDeOrigen` (`api/src/auth/csrf-origin.ts`): any state-changing method whose `Origin` isn't `FRONTEND_URL` gets a 403 before reaching a controller. A missing `Origin` is allowed on purpose — that is how Mercado Pago's webhook arrives, and it authenticates by HMAC, not by the cookie.

**`/vincular`: QR or code.** `useVinculacion` (`web/src/lib/vinculacion.ts`, shared by `/vincular` and the signup `/entrar/whatsapp`) holds `LinkState = "active" | "connecting" | "connected" | "expired" | "error"`, driven entirely by the API's SSE; each non-active state renders a card from `src/components/LinkStateCards.tsx`. A phone can't scan the QR on its own screen (LAU-11), so both pages pick the method by device — `useEsCelular` (`web/src/lib/dispositivo.ts`, `useSyncExternalStore`, `null` until hydrated) starts a phone on `TarjetaCodigo` and a computer on `TarjetaQr`, each with a link to the other — and both always show `AvisoNumeroPersonal` (the assistant answers every 1:1 chat of the linked number, friends and family included). The code is Baileys' `requestPairingCode` ("Vincular con el número de teléfono"): `POST /whatsapp/link/codigo` (session) or `POST /auth/whatsapp/alta/codigo` (`AltaGuard`) with `{ telefono }` → `WhatsappService.pedirCodigo` closes whatever socket wasn't linked, deletes the unregistered row, opens a fresh socket, waits for its first QR (`ESPERA_SOCKET_LISTO_MS`, the sign it already talked to WhatsApp) and returns `ABCD-1234`; WhatsApp pushes a notification to that phone to type it in. The number goes through `telefonoParaWhatsapp` (`auth/telefono.ts`: Argentina always with the 9; Mexico's 1 is unverified). Two traps: `requestPairingCode` fills `creds.me` **before** the code is entered, so `estaVinculado` (`whatsapp-auth-state.ts`) also requires `creds.registered` while a `pairingCode` is pending — otherwise a half pairing would be saved as `registered: true` and resumed at boot; and a socket in `modoCodigo` that closes before the code is entered is **not** reconnected (that would be a login with an unregistered `me`): its row is deleted and the SSE gets `expired`, which `TarjetaCodigo` shows in place with "Pedir otro código". `startLink` also starts clean, so switching back to the QR works. Each request pushes a notification to a phone nobody has proven yet, hence `MAX_CODIGOS_POR_NUMERO_HORA` (5) per `claveDeTelefono`, `MAX_CODIGOS_POR_CUENTA` (5 per 15 min) per account, one request at a time per account, and `MAX_CODIGOS_ALTA_POR_IP_HORA` on the signup (`AltaWhatsappService.pedirCodigo`, which also 401s once the user stopped being a pending signup). It answers 409 when `WhatsappSession.registered` is true in the DB, not only when the live socket is linked (a linked session has no socket while reconnecting). It never checks whether the number has an account (that stays in `asignarTelefono` at open, as with the QR). The socket presents itself as `NAVEGADOR_WHATSAPP` = `Browsers.ubuntu('Chrome')` on purpose: with the brand name (`Browsers.appropriate('Trato')`, which also sent the container's kernel as version) the QR worked but WhatsApp rejected every pairing code as "código incorrecto" (the socket then died with 408 after 2:40, when Baileys runs out of QR refs). So linked devices shows "Chrome (Ubuntu)", not "Trato" — don't rebrand it.

**Measuring WhatsApp latency.** Every line starting with `Tiempos WhatsApp` (`PREFIJO_TIEMPOS`, `api/src/whatsapp/metricas.ts`) is there to find where the time goes before optimizing: per answered burst `entrega` (WhatsApp's timestamp → Baileys handed it to us; this is where Baileys' 30 s event buffer after connecting showed up), `espera` (burst wait), `modelo`, `envio`; how long each connection took to open, every close with its code and how long an outage lasted once it recovers; and `MedidorDeGuardados` for the session saves (`filas`/size per save, a summary every 100 saves, immediately when one takes > 500 ms). Only ids and numbers — never the client's JID or text.

**WhatsApp connection (LAU-18).** Three things made the bot slow or silently mute, and each lives in its own place:
- *Socket options* (`WhatsappService.connect`): `syncFullHistory: false` + `shouldSyncHistoryMessage: () => false` (the history downloaded at link time was ignored anyway and held Baileys' event buffer for 30 s), `markOnlineOnConnect: false` (online, the owner's own phone stopped getting notifications; "escribiendo…" is still sent per chat), and `version` from `fetchLatestWaWebVersion` (cached 12 h, one fetch shared by every session resumed at boot; Baileys' bundled version if it fails). `getMessage` reads `MensajesEnviados` (`whatsapp/caches.ts`, the last `MAX_MENSAJES_ENVIADOS` (200) messages per account, filled by `enviar`, the one door every message to a client goes through; the owner's own chat — login codes — deliberately bypasses it) and `msgRetryCounterCache` is `CacheConVencimiento`, so a client whose phone couldn't decrypt a reply gets it re-sent instead of "Esperando el mensaje…". Memory only — single replica.
- *Reconnecting* (`whatsapp/reconexion.ts`, pure): `politicaDeCierre` turns a close code into `desvincular | codigo_vencido | reiniciar | reintentar | rendirse`, with the code-pairing check first so a pending code is still never reconnected. A linked session (`estaVinculado(creds)`) retries forever with `demoraDeReconexion` (exponential, equal jitter, `TECHO_RECONEXION_MS` 5 min); an unlinked one (a QR nobody scans) keeps the old cap of `MAX_RECONEXIONES_SIN_VINCULAR` (5). `connectionReplaced` retries no sooner than `MINIMO_TRAS_REEMPLAZO_MS` (1 min) — in a deploy overlap the old instance can steal the session back from the new one, which used to leave the new one mute until the next deploy. `badSession` is tolerated `MAX_SESIONES_MALAS_SEGUIDAS` (5) times in a row; that, `forbidden` and `multideviceMismatch` give up: the row is set `registered: false` (so neither the next boot nor `/vincular` resumes those credentials — `/vincular` starts from a fresh QR, since the web has no unlink button) and the owner gets `whatsapp_desconectado` asking to re-link. A linked session down for more than `MINUTOS_CAIDO_PARA_AVISAR` (10) gets one Sentry warning (`whatsapp-caido`, ids only) and one owner notification per outage; over WhatsApp it can't arrive, so it lands in the bell. Pending retries live in `reconexionesPendientes` and are cancelled by `cerrarSocket`, `unlink` and shutdown, and each retry first checks the row is still `registered`.
- *Saving the session* (`whatsapp-auth-state.ts`): `creds` stay encrypted in `WhatsappSession.authState`; every Signal key is its own `WhatsappClave` row (`@@id([userId, categoria, clave])`, FK to `WhatsappSession.userId` with cascade, so every existing `whatsappSession.deleteMany` — unlink, loggedOut, a lapsed code, `empezarDeCero`, account deletion — takes the keys too), each value `BufferJSON` + `encryptToken` on its own and each id stored as `idDeFila` (an HMAC with a subkey derived from `TOKEN_ENCRYPTION_KEY`: `session` ids are clients' JIDs, which used to sit inside the encrypted blob; Baileys always reads keys by id, never lists them). `keys.set` upserts/deletes only what changed in one transaction (`unnest` batches of 500, creating the session row first if Baileys writes pre-keys before the first `creds.update`), wrapped by `makeCacheableSignalKeyStore` so reads mostly hit memory. A pre-LAU-18 row (one `{ creds, keys }` blob) is split into rows the first time it loads, in one transaction — no re-linking. If `creds` no longer decrypt (rotated `TOKEN_ENCRYPTION_KEY`) it starts over and deletes that user's key rows. `esperarGuardados` (the per-session mutex) is what `transferirSesion` and the "connected" emit wait on, so key writes are covered too, not just `saveCreds`.

## Design system

`src/app/globals.css` is the whole design system, ported from an external `_ds_bundle.css` that is **not in this repo**. Three layers:

1. `:root` primitives (`--color-primitive-coral-500`, spacing, motion) — raw values.
2. `:root` semantic tokens (`--color-semantic-primary-default`, `--color-semantic-surface-page`) — reference primitives.
3. `@theme inline` — bridges semantics to Tailwind utilities: `bg-primary`, `text-ink`, `text-ink-secondary`, `text-muted`, `bg-page`, `bg-card`, `bg-sunken`, `border-line`, `font-display`, `rounded-md`, `shadow-md`, plus `success`/`warning`/`danger` families.

Use the Tailwind aliases, not raw `var(--color-…)`, except for tokens with no alias (info, `--color-primitive-neutral-200`). Radius and shadow tokens are prefixed `--ds-` to avoid self-referencing Tailwind's own namespaces — keep that prefix.

`next/font` variables (`--font-manrope`, `--font-jakarta`) must stay on `<html>` in `layout.tsx`, since `:root` tokens resolve them there.

`src/components/ui/` holds the primitives (`Button`, `Badge`) with variant/size lookup maps. `src/lib/cn.ts` is a dependency-free class joiner — no tailwind-merge, so don't rely on conflicting-class resolution.
